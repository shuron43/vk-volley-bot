# Разбор кода по Piecemeal Growth

Историческая запись завершённого разбора; результаты относятся к указанной дате.
Действующие контракты описаны в `docs/`.

Дата: 04.10.2026. Основание: [mode-piecemeal-growth.md](../docs/mode-piecemeal-growth.md).
Проверены Python-модули `src/`, их вызовы, тесты и описанные рабочие сценарии.

Критерий удаления: элемент не обслуживает текущий сценарий, дублирует
действующий контракт или молча подставляет данные при нарушении обязательного
условия. Сам по себе большой объём кода не означает лишнюю сложность.

## Удалено

| Элемент | Основание | Текущий путь |
|---|---|---|
| Необязательный `CardPublisher` в обработчиках и планировщике | `main()` уже создаёт общий экземпляр; запасные экземпляры имели независимые блокировки | Общий издатель передаётся обязательным аргументом |
| Аргумент `api` в функциях планировщика | Использовался только для запасного создания издателя | VK API принадлежит `CardPublisher` |
| `Storage.start_new_collection()` | Вызывался только тестами; обходил проверку ожидающего события и позволял открыть запись без дедлайна | `begin_event()` → `activate_event()` |
| `Storage.mark_opening()` и восстановление метаданных догадкой | `begin_event()` атомарно сохраняет время, источник и идентификатор отправки; обычный перезапуск их не теряет | Возобновление использует сохранённые значения; отсутствие обязательных полей вызывает ошибку |
| `Storage.remove_user()`, `remove_friend()` | В приложении не вызываются; участники уже используют отписку с правилом первых 30 минут | `withdraw_user()`, `withdraw_friend()`; админ удаляет через `remove_by_name()` |
| Отдельные геттеры ID карточки и `is_registration_open()` | Использовались только тестами либо вообще не вызывались | `snapshot()` и `active_collection()` |
| `help_text(compact=...)` | Флаг игнорировался; кнопка помощи уже содержит собственный короткий текст | `help_text()` |
| `format_event_start()` и `_MAX_NAME_LENGTH` в форматировании | Нет вызывающего кода; дата строится непосредственно в карточке, лимит проверяет хранилище | `format_registration_card()` и лимит в `Storage` |
| Запасная подпись неизвестного состояния карточки | Маскировала нарушение внутреннего контракта под закрытую запись | Тип `RegistrationState` и прямое обращение к подписи |
| Перехват отмены с немедленным `raise` в retry | Отмена и без этого проходит наружу; обработчик ловит только ошибки сети/API/диска | Естественное распространение отмены |

Тесты используют рабочие переходы событий. Старое состояние без дедлайна
проверяется через загрузку прежнего JSON, а не через метод, создающий такое
состояние в текущем приложении. Формат сохраняемых данных не изменён.

## Сохранено по текущим требованиям

- **Атомарная запись и `_commit()` после сохранения.** Защищают существующие
  данные при ошибке диска; тесты проверяют совпадение памяти и файла.
- **Блокировки и номер сбора.** Обработчики и планировщик работают одновременно;
  запрос профиля VK может завершиться уже после смены события. Это текущая
  конкурентность, а не подготовка к многопроцессному запуску.
- **Retry с дедлайном и сохранённым `random_id`.** Нужны для сетевой границы,
  повторной доставки и возобновления прерванного анонса.
- **Закрытие старого активного состояния без дедлайна.** В
  [плане и приёмке автозакрытия](2026-09-18-event-lifecycle-rfc.md) описан реальный случай такого JSON и
  ручная проверка исправления. Восстановление закрывает запись, сохраняя список.
- **Оба VK ID, проверка результатов удаления и замена карточки.** Рабочий ID
  карточки был реальной проблемой; отказы VK не должны считаться успешным
  удалением. Поведение замены уже входит в контракт карточки.
- **Peer guard, права админов, валидация расписания и лимиты.** Защищают
  внешние команды, текущие данные и документированные ограничения.
- **Ручные события, напоминания и первые 30 минут для отписки.** Это
  действующие пользовательские возможности с тестами, а не будущие расширения.

## Что не стоит обобщать сейчас

Повторяющаяся сборка `_StorageData` пока оставлена явной: у переходов различается,
какие поля сохраняются или сбрасываются. Универсальный механизм переходов
потребовал бы нового контракта и перенёс бы сложность в параметры.

Несколько свойств времени в `Config` также обслуживают действующее расписание.
Для этого бота не нужны общий реестр событий, универсальный роутер команд,
поддержка нескольких бесед или замена JSON на БД без нового требования.
