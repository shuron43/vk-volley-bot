# План следующих изменений

## Цель

Сделать регистрацию на событие устойчивой и понятной в реальном чате VK:

- время начала всегда сохраняется и автоматически закрывает запись;
- в чате существует ровно одна актуальная карточка бота;
- после команды участника карточка снова становится последним сообщением;
- кнопки отвечают через snackbar и не создают информационный спам;
- дата, время, состояние и участники видны непосредственно в карточке.

## Результат теста 17.09.2026

Ручное событие должно было закрыться в 22:20, но осталось открытым. В 22:32
зафиксировано следующее:

- запущенного процесса `python`/`uv` с ботом уже не было;
- временная сессия, из которой запускался бот, завершилась;
- в `data.json` осталось `registration_state="open"`;
- `event_starts_at` и `event_source` имели значение `null`;
- ID карточки был непригоден для редактирования: `status_message_id=0`,
  `status_conversation_message_id=null`.

Это указывает сразу на три проблемы. Тестовый процесс запускался неустойчивым
способом, событие не сохранило дедлайн, а VK-идентификатор карточки не был
получен. Точный момент завершения процесса установить нельзя, потому что у
запуска не было постоянного файла журнала.

## Этап 1. Надёжное автоматическое закрытие

### 1.1. Воспроизводимый запуск

Для ручного теста запускать бота как длительный процесс через Docker Compose
или отдельный скрытый процесс с PID-файлом и перенаправлением stdout/stderr в
`logs/bot.log`. После запуска проверять процесс, Long Poll и строки инициализации
планировщика. Временная терминальная сессия не должна считаться успешным
запуском.

### 1.2. Диагностика события

Добавить структурированные записи журнала для каждого перехода:

- создание события: источник, время анонса, время начала, `random_id`;
- успешная отправка и полученные `message_id`/`conversation_message_id`;
- переходы `closed → opening → open → closed`;
- рассчитанное время следующего пробуждения планировщика;
- отказ из-за пересечения или опоздавшей активации;
- восстановление состояния после перезапуска.

Добавить админ-команду `статус события`, которая показывает состояние,
сохранённое время начала и идентификаторы карточки. Во время разработки вывод
можно отправлять временным ответом, а в итоговом интерфейсе — показывать в
карточке или через админскую callback-кнопку.

### 1.3. Старые и повреждённые данные

При загрузке состояния `open`/`opening` без `event_starts_at` закрывать
регистрацию и писать предупреждение в журнал. Такое состояние нельзя оставлять
открытым: планировщик не знает, когда его завершать.

Перед публикацией анонса проверять, что `event_starts_at` и `event_source`
успешно сохранены. После отправки повторно проверять актуальность события, чтобы
поздний ответ VK не открыл уже закрытую регистрацию.

### 1.4. Проверка закрытия

Добавить тесты для случаев:

- ручное событие закрывается в заданную минуту;
- недельное событие закрывается в заданную минуту;
- бот перезапущен до начала и продолжает ожидание;
- бот запущен после начала и сразу закрывает запись;
- процесс завершился во время отправки анонса;
- VK ответил после времени начала;
- загружено `open` без дедлайна;
- ручное и недельное события пытаются пересечься.

Ручной приёмочный тест проводить с событием через 3–5 минут. Проверить JSON,
журнал, вид карточки до и после начала, а также отказ команды `записаться`
после закрытия.

## Этап 2. Единственная карточка события

### 2.1. Содержимое карточки

Целевой текст:

```text
🏐 Волейбол — запись открыта
📅 Вторник, 22 сентября 2026
🕢 Начало: 19:30
⏳ Запись закроется автоматически в 19:30

Участники: 2
1. Александр
2. Петя (друг)
```

После начала первая строка меняется на `🏐 Волейбол — запись закрыта`, строка
про будущее закрытие убирается, итоговый список сохраняется. Под карточкой
остаются кнопки **Записаться**, **Отписаться**, **Список** и **Помощь**.

### 2.2. Единый издатель карточки

Вынести создание, обновление и замену карточки в отдельный компонент. Он должен:

1. под одной блокировкой сформировать текст из одного снимка хранилища;
2. отправить новую карточку после текстовой команды, чтобы она стала последним
   сообщением;
3. сохранить оба VK ID новой карточки;
4. только после успешного сохранения удалить предыдущую карточку;
5. при callback-событии редактировать текущую карточку без нового сообщения;
6. переживать сетевую ошибку без потери ссылки на последнюю рабочую карточку.

Обычные сообщения участников, не являющиеся командами бота, карточку не
перемещают. Если сообщение вызвало действие бота, после обработки в чате снова
должна остаться одна карточка и она должна быть последней.

### 2.3. Корректные VK ID

Отдельно исследовать ответ `messages.send` для групповой беседы. Текущее
значение `message_id=0` нельзя использовать для `messages.edit`. Для отправки из
планировщика использовать вариант API, возвращающий
`conversation_message_id` (предварительно проверить `peer_ids`), либо получать
его дополнительным запросом. Хранилище должно считать карточку созданной только
после получения хотя бы одного рабочего ID.

### 2.4. Ответы без спама

- Нажатия кнопок: результат показывается через `show_snackbar`, карточка
  редактируется на месте.
- Успешные текстовые команды: отдельный ответ бота не отправляется; результат
  виден в новой последней карточке.
- Ошибка текстовой команды: короткое уведомление временно показывается внутри
  единственной карточки, после следующего действия исчезает.
- Справка: для кнопки используется snackbar; полная справка остаётся доступна
  по команде и показывается внутри карточки.

VK не предоставляет snackbar в ответ на обычное текстовое сообщение: для
`messages.sendMessageEventAnswer` нужен `event_id` от нажатия callback-кнопки.
Поэтому строго всплывающий ответ возможен только для кнопок. Если всплывающий
интерфейс нужен и для ввода имени друга, потребуется VK Mini App; в текущем
боте безопасный вариант — отражать результат текстовой команды в карточке без
дополнительного сообщения.

## Этап 3. Новый текст анонса

Анонс становится самой карточкой события и не содержит перечня текстовых
команд. Рекомендуемый вариант:

```text
🏐 Волейбол — запись открыта
📅 Вторник, 22 сентября 2026
🕢 Начало: 19:30
⏳ Запись закроется автоматически в 19:30

Участники: 0
Пока никто не записался.
```

Кнопки под сообщением объясняют основные действия. Добавление друга остаётся
текстовой командой `+ Имя` до появления отдельного интерфейса ввода.

## Этап 4. Критерии приёмки

- После анонса в чате ровно одна карточка бота.
- Карточка содержит полную дату, время, состояние и актуальный список.
- После любой обработанной текстовой команды карточка является последним
  сообщением.
- Callback-кнопки не создают новых сообщений и отвечают snackbar.
- Текстовые команды не создают отдельных информационных ответов.
- В момент начала состояние на диске становится `closed` даже после
  перезапуска или временной ошибки VK.
- Итоговый список после закрытия не очищается.
- Новый анонс очищает предыдущий список только после успешной публикации.
- Ручное событие нельзя создать поверх активного или пересекающегося окна.
- В хранилище всегда есть рабочий ID карточки и дедлайн активного события.
- Автотесты, типизация и линтер проходят; ручной тест подтверждён журналом и
  фактическим поведением VK.

## Порядок реализации

1. Устойчивый тестовый запуск и журналы.
2. Восстановление `open` без дедлайна и тест автоматического закрытия.
3. Получение рабочего `conversation_message_id` из отправки планировщика.
4. Единый компонент публикации карточки.
5. Перевод текстовых и callback-обработчиков на этот компонент.
6. Новый текст анонса и состояния карточки.
7. Интеграционные тесты гонок и перезапуска.
8. Повторный ручной тест в VK с событием через 3–5 минут.
