# Архитектура VK Volleyball Bot

## Общая структура

Проект построен по принципу **модульной монолитной архитектуры** с чётким разделением ответственности между компонентами. Бот использует фреймворк **vkbottle** для взаимодействия с VK API и **anyio** для структурированной конкурентности.

```
┌─────────────────────────────────────────────────────────────┐
│                        Пользователь (VK)                     │
└──────────────────────┬──────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    VK API (Long Poll)                        │
└──────────┬──────────────────────────────────┬───────────────┘
           │                                  │
           ▼                                  ▼
┌──────────────┐                    ┌──────────────────────┐
│   bot.py     │                    │    scheduler.py      │
│  Хендлеры    │                    │  Планировщик         │
│  сообщений   │                    │  (еженедельный)      │
└──────┬───────┘                    └──────────┬───────────┘
       │                                      │
       ▼                                      ▼
┌─────────────────────────────────────────────────────────────┐
│                      storage.py                              │
│              JSON-хранилище участников                       │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│                     config.py                                │
│            Конфигурация из переменных окружения             │
└─────────────────────────────────────────────────────────────┘
```

## Потоки данных

### 1. Интерактивный поток (сообщения в чате)

1. Пользователь пишет сообщение в групповой чат VK **или нажимает inline-кнопку**
2. VK API доставляет событие через Long Poll:
   - Текст → `message` event
   - Кнопка → `message_event` (callback)
3. **vkbottle** (`bot.py`) маршрутизирует событие по правилам:
   - Exact text / Regex → text handlers
   - `PayloadRule` → callback handlers
4. Общий peer-guard сравнивает `event.peer_id` с `CHAT_PEER_ID`; чужие события прекращаются до любых чтений, записей или ответов
5. Хендлер получает `storage.active_collection()` через общие хелперы `join_user` / `add_friend_by_name`. В состояниях `closed` и `opening` пользователь получает отказ без обращения к VK API. При добавлении `expected_collection` повторно проверяется под блокировкой хранилища: задержавшийся запрос не может попасть в следующий сбор.
6. `Storage` атомарно обновляет JSON-файл на диске (tempfile + replace). В одном коммите сохраняются участники, жизненный цикл, дедлайн и оба VK ID карточки.
7. `CardPublisher` сериализует все видимые изменения своей блокировкой:
   - после текстовой команды отправляет новую карточку через `peer_ids`, сохраняет рабочие ID и только затем удаляет предыдущую;
   - после callback редактирует текущую карточку, а результат кнопки показывает через `show_snackbar`;
   - при ошибке редактирования публикует замену, не теряя ссылку на последнюю рабочую карточку.

### 2. Поток планировщика (анонс + закрытие + напоминание)

1. `scheduler.py` вычисляет ближайшие события:
   - **Анонс** — день/время из `COLLECT_WEEKDAY`/`COLLECT_TIME`
   - **Начало тренировки** — точный `event_starts_at`, сохранённый в JSON
   - **Напоминание** — день/время из `REMIND_WEEKDAY`/`REMIND_TIME` (если включено)
2. Выбирает ближайшее событие и засыпает на вычисленный интервал (`anyio.sleep`)
3. По пробуждению:
   - Если наступил **анонс**: вычисляет следующее начало из `EVENT_WEEKDAY`/`EVENT_TIME`, атомарно вызывает `storage.begin_event(...)`, публикует карточку и после получения рабочего `message_id` или `conversation_message_id` вызывает `storage.activate_event(...)`.
   - Если наступило **начало тренировки**: вызывает `storage.close_registration()` и редактирует каноническую карточку без нового сообщения.
   - Если наступило **напоминание**: переиздаёт каноническую карточку последним сообщением без изменения регистрации.
4. Цикл повторяется бесконечно

Ручная команда использует тот же переход `begin_event` и поэтому не может
открыться поверх `opening`/`open`. Дополнительно её начало обязано быть раньше
следующего еженедельного анонса. Если бот был выключен во время начала, при
старте он сравнивает сохранённый `event_starts_at` с текущим временем и сразу
закрывает просроченную запись.

Подробнее о сбоях — в разделе [Жизненный цикл регистрации](#жизненный-цикл-регистрации).

## Конкурентность

```
main.py
└── anyio.create_task_group()
    ├── run_scheduler(...)   # поток планировщика
    └── bot.run_polling()    # поток Long Poll
```

Оба потока выполняются в рамках одного **TaskGroup** from `anyio`. Это означает:
- Если один поток падает с исключением, оба завершаются
- Graceful shutdown при получении сигнала SIGINT/SIGTERM
- `Storage` является общим ресурсом; все публичные методы асинхронны и защищены `asyncio.Lock`
- Планировщик устойчив к сбоям VK API: публикация карточки и напоминание повторяются каждые 5 минут; анонс не повторяется после дедлайна
- До успешной отправки анонса `mark_opening` держит состояние `opening`, поэтому перезапуск бота или повторный retry не теряет участников предыдущего сбора

## Хранилище

Внутреннее представление: `_StorageData` хранит участников, состояние регистрации, `status_message_id`, `status_conversation_message_id`, номер сбора, `announcement_random_id`, `event_starts_at` и источник события (`weekly`/`manual`). Старые файлы читаются со значениями по умолчанию. Активное старое состояние без `event_starts_at` при запуске принудительно закрывается и отмечается в журнале.

При старте планировщик возобновляет сохранённое `opening` до ожидания следующего события. Все попытки анонса используют сохранённый `random_id`. Если активация после отправки не удалась, опубликованная, но не зафиксированная карточка удаляется, а состояние `opening` восстанавливается при следующем запуске. Полностью пропущенные во время простоя события автоматически не воспроизводятся.

После любого успешного изменения списка через текст, кнопки или админ-команды обновляется каноническое сообщение, если его ID известен. Чтение списка и отправка правок сериализованы отдельной блокировкой; ошибка обновления логируется и не отменяет сохранённую запись.

Формат JSON-файла (`data.json`):

```json
{
  "participants": [
    { "kind": "user", "vk_id": 123456789, "name": "Алексей" },
    { "kind": "friend", "name": "Андрей" }
  ],
  "registration_state": "open",
  "status_message_id": 456,
  "status_conversation_message_id": 73,
  "event_starts_at": "2026-09-22T19:30:00",
  "event_source": "weekly"
}
```

### Атомарность записи

`_save()` не пишет напрямую в целевой файл. Вместо этого:
1. Сериализует снимок JSON во временный файл (`*.tmp`)
2. Вызывает `replace()` для атомарной замены

При падении процесса во время записи оригинальный файл остаётся неповреждённым.
`_commit()` сначала сохраняет снимок, затем заменяет живое состояние. Поэтому:

- Ошибка записи не создаёт расхождение между памятью и диском.
- `_load()` сохраняет `opening` и участников; при старте планировщик возобновляет незавершённое открытие с сохранённым идентификатором отправки.

### Жизненный цикл регистрации

Три состояния и методы, которые их переключают:

```
        storage.begin_event(start, source)
closed ───────────────────────▶ opening
                                  │
                                  │ storage.activate_event(message_id, start)
                                  ▼
                                 open
                                  │
                                  │ storage.close_registration() в момент начала
                                  ▼
                                closed
```

| Метод | Эффект |
|-------|--------|
| `begin_event(start, source)` | Если нет активного события, сохраняет `opening`, время, источник и `random_id` |
| `mark_opening()` | Восстанавливает/дополняет незавершённое состояние `opening` |
| `start_new_collection(message_id)` | Низкоуровневый переход в новый пустой список |
| `activate_event(message_id, expected_start, conversation_message_id=...)` | Открывает только всё ещё актуальное `opening`, сохраняет оба ID и защищает от позднего ответа VK |
| `close_registration()` | Переводит в `closed`, сохраняя итоговый список и время события |
| `close_missing_deadline()` | Закрывает повреждённое активное состояние без времени начала |
| `set_status_message_id(message_id, conversation_message_id=...)` | Сохраняет адрес текущей карточки после безопасной замены |
| `clear()` (админ) | Очищает только `participants`. **Не** используется планировщиком — это админ-команда |

Все методы синхронизированы через `asyncio.Lock`, поэтому сценарии
`scheduler` + `CardPublisher` + админ-команды не
портят друг друга.

### Почему JSON, а не БД?

Проект находится в **MVP-стадии**. JSON выбран по следующим причинам:
- **Простота**: нулевая конфигурация инфраструктуры
- **Прозрачность**: файл можно редактировать вручную
- **Достаточность**: для одного чата и одного события в неделю JSON вполне адекватен
- **Мигрируемость**: при переходе на SQLite/PostgreSQL структура `Entry` остаётся

## Типизация

Проект использует строгую статическую типизацию:
- **Pydantic** для валидации конфигурации и данных хранилища
- **basedpyright** в режиме `all` — проверяет все типы без исключений
- **Ruff** с включёнными почти всеми правилами (линтинг, безопасность, стиль)
- Используется `assert_never` для exhaustive match — если добавится новый тип `Entry`, компилятор заставит обработать его во всех `match/case`

## Безопасность

- Токен VK хранится только в переменных окружения (`.env` в `.gitignore`)
- Все команды и callback-события ограничены одним настроенным `CHAT_PEER_ID`
- `random_id` для VK API генерируется через `secrets.randbelow()` или `secrets.randbits()`
- В рабочем коде нет `eval`/`exec`
- JSON разбирается в типизированную Pydantic-модель; данные с неверной схемой отклоняются при старте

## Масштабируемость

Текущая архитектура подходит для **одного сообщества / одного чата**.

Для масштабирования на несколько чатов потребуется:
1. Переход на SQLite/PostgreSQL для изоляции данных по чатам
2. Динамическая конфигурация `CHAT_PEER_ID` (таблица `chats`)
3. Параллельный запуск нескольких экземпляров бота или переход на webhook-режим
4. Кеширование имён пользователей VK (чтобы не дергать API при каждом `+`)

## Тестируемость

Каждый модуль изолирован и покрыт тестами:
- `Config` — `tests/test_config.py`: обязательные поля, расписание, admin ID и безопасный путь к данным
- `Storage` — `tests/test_storage.py`: операции add/remove/clear на временном файле (`tmp_path`)
- `bot.py` — `tests/test_bot.py` и `tests/test_bot_handlers.py`: peer-guard и зарегистрированные хендлеры с реальным временным `Storage`
- `scheduler.py` — `tests/test_scheduler.py`: чистая логика `_next_target` без sleep, dual-event loop (collect + remind)
- `test_smoke.py` — интеграционный импорт всех модулей
