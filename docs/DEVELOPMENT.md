# Процесс разработки и память проекта

Эти правила действуют для дальнейшей разработки. Краткие инструкции и полный
список актуальных документов находятся в корневом [AGENTS.md](../AGENTS.md),
который агент получает в контекст каждой сессии.

## Работа над изменением

1. Прочитать [Piecemeal Growth](mode-piecemeal-growth.md) и
   [Focused Specs](focused-specs.md) в начале сессии разработки. По списку
   в `AGENTS.md` выбрать только документы, относящиеся к текущей задаче.
2. Установить текущую потребность: запрос пользователя, исполняемое требование,
   рабочий сценарий или воспроизводимый сбой. Проверить состояние Git;
   все изменения выполнять в отдельной ветке `codex/`, сохраняя чужие правки.
3. Для изменения поведения сформулировать минимальный пользовательский или
   сохраняемый исход и его спек. Бизнес-сценарий содержит `Given`, один запрос
   и один `Then`; независимые исходы получают собственные сценарии.
4. Проверить поведение через границу продукта. Для бота это настоящие
   `message_new`/`message_event`, payload фактической клавиатуры, маршрутизатор,
   хранилище и издатель карточки; подменяется внешний VK API. Сохранение
   подтверждается чтением новым `Storage`. Технические контракты протокола,
   записи, перезапуска и освобождения ресурсов проверяются отдельно.
5. Исправить приложение локально до соответствия спеку. Не заменять бизнес-код
   заглушкой ради зелёного сценария и не подгонять обещанный исход под ошибку.
   Добавлять абстракцию, настройку или запасной путь только при текущей
   потребности. Защиту данных, внешних команд и известных отказов сохранять.
6. Проверить, что наблюдения защищают заявленный исход, а не внутренние имена,
   стили или несущественный текст. Точная пустота и порядок нужны там, где
   обещаны отсутствие спама/изменений, права доступа или порядок внешних действий.
   Контрольную поломку использовать при сомнении, что спек обнаружит регрессию;
   делать её в памяти или временно и восстановить приложение до завершения.
7. Выполнить проверки по [TESTING.md](TESTING.md), соответствующие изменению.
   Для документации проверить ссылки, индексы и diff; новые программные тесты
   только ради перемещения Markdown не нужны. Для кода выполнить проверки CI
   из `AGENTS.md`. Обновить затронутое актуальное знание и сообщить результат
   проверок вместе с существенными ограничениями.

Приложение должно соответствовать действующим BDD. Тесты реализации полезны для
инфраструктуры, но вызов внутренней функции сам по себе не доказывает бизнес-исход.
Сопутствующие руководства `feature-clause-writing.md` и `ui-design.md`, упомянутые
в Focused Specs, в проект не входят: сейчас нет clause-backed или HTML-спеков.
Условные ссылки на них не добавляют задач в текущий процесс разработки бота.

## Актуальные знания и история

`docs/` содержит действующие правила, контракты и инструкции, которые могут
пригодиться любой сессии. Здесь пишут о том, как система работает сейчас:
поведение, ограничения, команды проверки и эксплуатации. Новое устойчивое
знание добавляют в подходящий существующий документ. При добавлении, удалении
или переименовании документа обновляют его описание в `AGENTS.md` и
[индексе docs](README.md) в той же правке.

`records/` содержит датированную историю: эксперимент, инцидент, postmortem,
завершённый или отменённый RFC, отчёт ревью. Запись указывает вопрос/контекст,
что проверялось, результат и ограничения доказательства. Кодовые имена и
команды отражают состояние на момент записи. После завершения их не меняют
вслед за рефакторингом; новый вывод становится новой записью.

В начале сессии читают текущие знания, а не всю историю. В `records/` идут только
при явной необходимости для текущего вопроса или по запросу пользователя,
сначала называя причину. Старый план не создаёт новую работу. При противоречии
сначала проверяют текущий код, BDD и `docs/`; архив не переопределяет их.
Если план полностью выполнен, его исторический текст переносят в `records/`,
а актуальные контракты оставляют в `docs/`. Таблицы результатов запусков и
журналы экспериментов не дописывают в актуальные руководства.

## Временная инлайн-память

На текущей стадии агент может без отдельного согласования оставить рядом с кодом
якорный комментарий с единственным тегом `AGENT-NOTE`. Он фиксирует обнаруженный
сюрприз или локальное ограничение, которое ещё не оформлено в `docs/`: наблюдение,
его причину и, когда полезно, способ проверки. Заметка объясняет, почему здесь
нужна осторожность. Предположение, план будущей функции и пересказ очевидного
кода для этого не подходят.

Каждая строка заметки — отдельный комментарий с префиксом `# AGENT-NOTE:`.
Не добавлять тег в конец строки с исполняемым кодом: все строки заметок должны
удаляться без удаления кода. Например:

```python
# AGENT-NOTE: <наблюдаемое ограничение>; <причина или способ проверки>.
```

Поиск всех заметок из корня проекта одной командой:

```powershell
rg -n '^[ \t]*# AGENT-NOTE:' src tests scripts
```

Заметки — временная память. Когда они повторяются, затрагивают несколько мест
или становятся устойчивым знанием, собрать их этой командой, сверить с кодом и
BDD, удалить устаревшие и дедуплицировать оставшиеся. Общие ограничения перенести
в подходящий документ `docs/` и обновить индексы, если создан новый документ.
Детали эксперимента при необходимости оставить в датированной записи `records/`.
После переноса убрать исходные комментарии. Не хранить одно правило одновременно
в заметках и нескольких документах.

После проверки переноса удалить все строки заметок одной PowerShell-командой
(один конвейер, сохраняющий остальные строки UTF-8 файлов):

```powershell
rg -l '^[ \t]*# AGENT-NOTE:' src tests scripts | ForEach-Object {
    $noteFile = (Resolve-Path -LiteralPath $_).Path
    $noteText = [IO.File]::ReadAllText($noteFile)
    $noteText = [regex]::Replace($noteText, '(?m)^[ \t]*# AGENT-NOTE:[^\r\n]*(?:\r?\n|$)', '')
    [IO.File]::WriteAllText($noteFile, $noteText, [Text.UTF8Encoding]::new($false))
}
```

Этот механизм не заменяет документацию. Уже описанные долговременные контракты
не размечают временными тегами; обычные поясняющие комментарии и lint/type pragmas
остаются самостоятельной частью кода.
